# Verify registry pack downloads

Status: ready-for-agent
Phase: P1
Category: enhancement
Depends on: 05

## Problem

- `RegistryPackVersion.Checksum` (`pkg/query/compliance/registry.go`) is never populated.
  `fetchPackVersions` builds versions from GitHub release tarballs, which carry no checksum, so
  no registry pack download is actually verified.
- External packs are meant to be first-class, so an "official packs only" checksum table is not
  enough.

## Change

Pick one, or combine them:

- **Published asset.** Packs publish a checksum release asset, such as
  `<pack>.tar.gz.sha256` or one checksums file per release. `fetchPackVersions` reads it into
  `Checksum`, and `DownloadPack` downloads that release asset rather than the auto-generated
  source tarball.
- **Lockfile pin.** A local lockfile records the SHA-256 on first install (trust on first use),
  and a later download of the same version that hashes differently fails.

GitHub's auto-generated source tarballs are not guaranteed to be byte-stable across time, so
pinning their hash can produce false mismatches. That favors published assets over pinning
auto-tarballs.

## Acceptance

- A pack whose published checksum or pinned hash does not match is rejected.
- Tests cover a matching download, a mismatch, and a missing checksum asset.

## Agent Brief

**Category:** enhancement
**Summary:** Verify every registry pack download against a published checksum, pin installed
hashes in a lockfile, and refuse unverified packs unless the user opts in.

**Current behavior:**
`RegistryClient.fetchPackVersions` builds each `RegistryPackVersion` from the GitHub releases
API using the release's auto-generated source tarball (`TarballURL`), so
`RegistryPackVersion.Checksum` is always empty. `downloadAndExtract` verifies SHA-256 only when
`Checksum` is set; otherwise it writes a warning and installs anyway. In practice no
`corkscrew pack install` download is verified, and packs are discovered by GitHub topic search,
so any tagged repo can supply SQL. There is no lockfile.

**Desired behavior:**
- **Published checksums.** When reading releases, if a release has a `checksums.txt` asset
  (sha256sum format: `<64 hex>  <asset name>` per line, goreleaser convention), the client
  selects the pack tarball **release asset** listed in it (a `.tar.gz` asset; not the
  auto-generated source tarball), sets `DownloadURL` to that asset and `Checksum` to its hash.
  A `<asset>.sha256` sidecar is also accepted. `checksums.txt` is size-bounded and parsed
  strictly (malformed lines are an error, not skipped).
- **Verification.** A download whose SHA-256 differs from `Checksum` is rejected before
  extraction, and nothing is installed.
- **No checksum.** If a version has no published checksum, install fails with an error that
  names the pack and version and mentions `--allow-unverified`. With
  `corkscrew pack install --allow-unverified`, it warns and installs (the source tarball is
  acceptable then).
- **Lockfile.** Every successful install (verified or not) records source, namespace, version,
  download URL and SHA-256 in a lockfile next to the installed packs. A later download of a
  version already in the lockfile must hash to the pinned value, or it fails with a mismatch
  error, even with `--allow-unverified`. A pin is replaced only by a deliberate, documented
  action (for example uninstalling the pack, or an explicit re-pin flag); `--force` alone
  must not silently re-pin. Lockfile writes are atomic. The lockfile shape keys entries by
  source so git and future OCI sources (which have native digests) fit without a format change.
- Pack dependencies installed transitively follow the same rules.

**Key interfaces:**
- `RegistryPackVersion` — `Checksum` and `DownloadURL` become populated from release assets.
- `GitHubRelease` — needs the release `assets` list (name, browser download URL, size).
- `RegistryClient.DownloadPack(ctx, namespace, version, destDir)` — gains a way to allow
  unverified installs (option or field), and consults/updates the lockfile.
- `corkscrew pack install` — new `--allow-unverified` flag; help text documents it.
- The `RegistryError` style for new failure kinds (checksum mismatch, missing checksum,
  lockfile mismatch), so callers can tell them apart.

**Acceptance criteria:**
- [ ] A release with `checksums.txt` and a matching tarball asset installs, and the lockfile
      records its hash.
- [ ] A tarball whose hash does not match `checksums.txt` is rejected and nothing is written to
      the install directory.
- [ ] A release with no checksum asset fails without `--allow-unverified`, and installs with a
      warning (and a lockfile pin) with it.
- [ ] Re-downloading a pinned version that hashes differently fails, with and without
      `--allow-unverified`.
- [ ] A malformed or oversized `checksums.txt` is an error.
- [ ] `<asset>.sha256` sidecars are accepted.
- [ ] Tests use an `httptest` server for the releases API and assets (no network), and cover
      match, mismatch, missing checksum asset, and lockfile mismatch.
- [ ] The pack-author docs (or the README section on packs) explain how to publish
      `checksums.txt` with a release.

**Out of scope:**
- OCI pack sources (only keep the lockfile shape ready for them).
- Signature verification (cosign/minisign/GPG); this issue is integrity, not authenticity.
- Changing GitHub topic-search discovery.
- Release automation for the in-repo official packs (they ship with the binary).
